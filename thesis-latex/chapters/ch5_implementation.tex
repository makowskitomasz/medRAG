\chapter{Implementation}
\label{cha:implementation}

This chapter describes the concrete engineering decisions made while building
the \medrag{} prototype.  Rather than walking through the code exhaustively,
the focus is on the non-trivial choices --- ones that required a genuine trade-off
or that differ from a textbook solution.  Six topics are covered: the technology
stack and its rationale~(\S\ref{sec:tech_stack}), the provider abstraction for
dense embeddings~(\S\ref{sec:embedding_abstraction}), the hybrid retrieval
mechanism and its empirical tuning~(\S\ref{sec:hybrid_search}), the Server-Sent
Events streaming architecture~(\S\ref{sec:sse_streaming}), the asynchronous
integration of the RAGAS evaluation framework~(\S\ref{sec:ragas_integration}),
and the continuous-integration and deployment pipeline~(\S\ref{sec:cicd}).

% ------------------------------------------------------------
\section{Technology Stack}
\label{sec:tech_stack}

\medrag{} is implemented as a collection of fourteen loosely-coupled
microservices.  \cref{tab:services} lists the services, their network ports,
and their principal responsibilities; the design rationale for the decomposition
is discussed in \cref{cha:system_design}.  This section covers the technology
choices that span the entire codebase.

\paragraph{Python back-end services.}
All thirteen Python services are written against \textbf{Python~3.12} and
served with \textbf{FastAPI}.  FastAPI was chosen for its first-class support
for Python's \texttt{async}/\texttt{await} model, automatic OpenAPI schema
generation, and the lightweight dependency-injection mechanism (\texttt{Depends}),
which is used throughout to inject provider-specific strategy objects without
coupling callers to concrete types.

Package management is handled exclusively by \textbf{uv}, the Rust-based
package resolver and installer.  Compared with the traditional
\texttt{pip}+\texttt{venv} toolchain, \texttt{uv} resolves and installs a
typical service's dependency graph in under three seconds --- an order of
magnitude faster than \texttt{pip}, which makes a noticeable difference in CI
build times and iterative development.  Each service carries its own
\texttt{pyproject.toml} and \texttt{uv.lock} file; lock files are committed
to the repository to guarantee reproducible builds.

Service configuration is declared through \textbf{pydantic-settings}: a typed
\texttt{Settings} class reads values from environment variables and from an
optional \texttt{.env} file.  This gives strong validation --- a malformed
integer or missing mandatory variable fails fast at startup --- while remaining
fully compatible with twelve-factor conventions.

Observability is provided by \emph{structured JSON logging} implemented in the
shared library at \texttt{shared/logger.py}.  Every log record includes at
least the fields \texttt{service}, \texttt{level}, \texttt{message}, and
\texttt{trace\_id}.  The trace identifier is extracted from the incoming
\texttt{X-Trace-Id} HTTP header at the gateway and propagated through all
inter-service calls and through RabbitMQ message properties, enabling
end-to-end correlation of a single user query across the entire call graph.

\paragraph{Front-end.}
The web client is a \textbf{Next.js~15} application written in TypeScript.
UI components are drawn from the \textbf{shadcn/ui} library --- a collection of
accessible, unstyled primitives built on top of Radix UI --- styled with
\textbf{Tailwind CSS}.  The App Router is used throughout; streaming responses
from the generation service are consumed via the browser's native
\texttt{EventSource} API (see \S\ref{sec:sse_streaming}).

\paragraph{Machine-learning dependencies.}
Dense vector embeddings are produced via the \textbf{OpenAI Embeddings API};
the system also supports a local deployment using \textbf{BGE-M3}
(\texttt{BAAI/bge\allowbreak-m3})~\cite{chen2024bge} through the
\texttt{sentence-transformers} library.  The cross-encoder re-ranker uses
\textbf{BGE-reranker-v2-m3} via the same library's \texttt{CrossEncoder}
interface.  Large Language Model inference is
delegated to the OpenAI API; the default model used in experiments
is \texttt{gpt-5-nano} (alternatively \texttt{gpt-oss-120b}), configurable via the \texttt{LLM\_MODEL}
environment variable.

\paragraph{Data stores and messaging.}
Weaviate~1.27 serves as the vector database; the Python client v4 is used,
which features a type-safe query builder API replacing the older GQL
interface.  MongoDB~7 stores all document metadata, project configuration, and
evaluation results; access is through PyMongo.  Asynchronous inter-service
messaging uses RabbitMQ~3.13; the \texttt{aio-pika} library provides an
\texttt{asyncio}-native AMQP client.

\paragraph{Containerisation.}
Every service is packaged in a \emph{multi-stage Docker build}: a builder
stage installs dependencies into a virtual environment using \texttt{uv sync},
and a final stage copies only the resulting \texttt{.venv} and application
source into a lean \texttt{python:3.12-slim} image.  A non-root user
\texttt{appuser} (UID~1000) is created and set as the default, which is a
Docker security best practice.  The entire system is orchestrated with a single
\texttt{docker-compose.yml} file that declares health-check probes for each
service, ensuring deterministic start-up ordering.

\section{Embedding Provider Abstraction}
\label{sec:embedding_abstraction}

Empirical evaluation of RAG systems often requires swapping embedding models.
Doing this in a tightly coupled codebase is error-prone and typically requires
touching multiple files.  \medrag{} avoids this by implementing an
\emph{embedding provider abstraction} that follows the Strategy design
pattern~\cite{gamma1994design}: a single abstract base class defines the
interface, and concrete subclasses encapsulate all provider-specific logic.

\subsection{Interface Definition}

\cref{lst:embedding_abc} shows the abstract base class and the signatures of the
three concrete providers.  The interface consists of a single \texttt{async}
method, \texttt{embed\_texts}, which accepts a list of strings and returns a list
of floating-point vectors.  Accepting batches rather than single strings allows
providers to exploit vectorised inference efficiently.

\begin{figure}[htbp]
  \centering
\begin{lstlisting}[language=Python,
  caption={Embedding provider strategy: abstract interface and concrete class
    signatures (simplified).},
  label={lst:embedding_abc}]
from abc import ABC, abstractmethod

class EmbeddingProvider(ABC):
    """Uniform interface for all dense embedding back-ends."""

    @abstractmethod
    async def embed_texts(
        self, texts: list[str]
    ) -> list[list[float]]:
        """Return one embedding vector per input text."""
        ...

class LocalBGEProvider(EmbeddingProvider):
    """BAAI/bge-m3 via sentence-transformers (local inference)."""
    async def embed_texts(self, texts: list[str]) -> list[list[float]]: ...

class CohereProvider(EmbeddingProvider):
    """Cohere Embed v3 via the Cohere Python SDK (API call)."""
    async def embed_texts(self, texts: list[str]) -> list[list[float]]: ...

class OpenAIProvider(EmbeddingProvider):
    """text-embedding-3-small via the OpenAI Python SDK (API call)."""
    async def embed_texts(self, texts: list[str]) -> list[list[float]]: ...
\end{lstlisting}
  \caption[Embedding provider strategy pattern.]{Embedding provider strategy: abstract interface with three concrete implementations (local BGE-M3, Cohere, OpenAI).}
  \label{fig:embedding_strategy}
\end{figure}

\subsection{Provider Selection and Injection}

The active provider is chosen at application start-up by reading the
\texttt{EMBEDDING\_PROVIDER} environment variable.  A factory function maps
the string value to the corresponding class, instantiates it (loading the model
weights for \texttt{LocalBGEProvider}, or initialising the SDK client for the
API-based providers), and stores the instance in the FastAPI application state.
All endpoints that require embeddings declare a \texttt{Depends(get\_provider)}
parameter; FastAPI resolves this dependency automatically.  No
business-logic code imports a concrete provider class --- only the abstract base
class --- so changing the provider is an environment variable change,
nothing more.

\subsection{Provider Trade-offs}

\cref{tab:embedding_providers} compares the three providers across the
dimensions most relevant for research experimentation: monetary cost,
inference latency, embedding dimensionality, and operational complexity.

\begin{table}[htbp]
  \centering
  \caption[Comparison of embedding providers supported by \medrag{}.]{Embedding provider comparison: model, dimensions, cost per 1,000 tokens, and indicative batch latency on CPU.}
  \label{tab:embedding_providers}
  \begin{tabularx}{\textwidth}{lXXXX}
    \toprule
    \textbf{Provider} & \textbf{Model} & \textbf{Dimensions} &
    \textbf{Cost (per 1\,000 tokens)} & \textbf{Latency (batch)} \\
    \midrule
    \texttt{local\_bge} & \texttt{BAAI/bge-m3}
      & 1\,024 & Free (compute only) & $\sim$50\,ms (CPU) \\

    \bottomrule
  \end{tabularx}
\end{table}

The default provider is \texttt{local\_bge}.  BGE-M3 supports multilingual
text, produces competitive retrieval quality on the BEIR benchmark, and incurs
no per-token monetary cost --- which matters when embedding tens of thousands
of document chunks.  The Cohere and OpenAI providers are there for ablation
studies and for deployments where a GPU is not available.

\section{Hybrid Search and Alpha Tuning}
\label{sec:hybrid_search}

Retrieval quality is central to the performance of any RAG system, and a hybrid
search strategy --- combining dense vector similarity with sparse lexical matching ---
consistently outperforms either mode alone across diverse question
types~\cite{thakur2021beir}.  This section describes how hybrid search is
implemented in \medrag{} and how the blending parameter was tuned.

\subsection{Weaviate Hybrid Query}

Weaviate's hybrid query API accepts a query string, a pre-computed query embedding,
and a scalar parameter \(\alpha \in [0, 1]\) that controls the balance between the
two retrieval signals.  \cref{lst:hybrid_query} shows the retrieval call as it
appears in the \texttt{retrieval} service.

\begin{lstlisting}[language=Python,
  caption={Hybrid retrieval query issued to Weaviate.  The \texttt{alpha}
    parameter and \texttt{top\_k} are read from the project's stored
    settings, enabling per-project tuning without code changes.},
  label={lst:hybrid_query}]
response = collection.query.hybrid(
    query=query_text,           # BM25 tokenised internally by Weaviate
    vector=query_embedding,     # pre-computed by the embedding service
    alpha=settings.alpha,       # 0.0 = pure BM25, 1.0 = pure vector
    limit=settings.top_k,       # candidates before re-ranking
    return_metadata=MetadataQuery(score=True),
    filters=Filter.by_property("project_id").equal(project_id),
)
\end{lstlisting}

Internally, Weaviate computes a BM25 ranking score and a cosine-similarity
vector score independently for each candidate document, then fuses them via
\emph{Reciprocal Rank Fusion} (RRF)~\cite{cormack2009rrf} with \(k = 60\):

\begin{equation}
  \mathrm{RRF}(d) \;=\;
    \alpha \cdot \frac{1}{k + r_{\text{vec}}(d)} \;+\;
    (1 - \alpha) \cdot \frac{1}{k + r_{\text{BM25}}(d)},
  \label{eq:rrf_ch5}
\end{equation}

\noindent where \(r_{\text{vec}}(d)\) and \(r_{\text{BM25}}(d)\) are the
rank positions of document \(d\) in the vector and BM25 rankings respectively.
Documents are returned in decreasing order of the combined RRF score.

\subsection{Empirical Alpha Tuning}

The optimal \(\alpha\) depends on the query distribution and the corpus.
To find an appropriate value for the HotpotQA experimental setting, a grid search
was conducted over \(\alpha \in \{0.0, 0.25, 0.5, 0.75, 1.0\}\) on a development
split of 100 randomly sampled questions from HotpotQA.  The primary optimisation
target was \emph{Faithfulness}, the most safety-critical metric for the
drug-interaction domain.  \cref{tab:alpha_grid} reports the results.

\begin{table}[htbp]
  \centering
  \caption[Effect of hybrid search \(\alpha\) on RAGAS metrics.]{Effect of hybrid search \(\alpha\) on Faithfulness and Context Recall (100 HotpotQA dev questions; higher is better).}
  \label{tab:alpha_grid}
  \begin{tabularx}{\textwidth}{lXX}
    \toprule
    \(\alpha\) & \textbf{Faithfulness} & \textbf{Context Recall} \\
    \midrule
    0.00 (pure BM25)    & 0.821 & 0.748 \\
    0.25                & 0.854 & 0.791 \\
    0.50 (equal blend)  & \textbf{0.912} & \textbf{0.837} \\
    0.75                & 0.889 & 0.821 \\
    1.00 (pure vector)  & 0.863 & 0.796 \\
    \bottomrule
  \end{tabularx}
\end{table}

The equal-weight blend (\(\alpha = 0.5\)) produced the highest scores on both
metrics.  This makes sense: HotpotQA questions frequently contain named entities
such as drug names, gene symbols, and numeric dosages, for which BM25's exact-match
signal is particularly valuable.  Pure vector retrieval captures semantic paraphrases
but tends to retrieve thematically related documents that omit the specific entity
needed to answer the question.  Pure BM25, on the other hand, fails when the question
is phrased differently from the target passage.  The hybrid approach benefits from
both signals simultaneously.

The default \(\alpha = 0.5\) is used in all experiments reported in
\cref{cha:evaluation}.  Per-project overrides are supported: the
\texttt{admin} service exposes an endpoint that updates the \texttt{alpha}
field in the project's MongoDB settings document, and the retrieval service
reads this value at query time.

\subsection{Retrieval Top-k and Re-ranking}

The retrieval service returns \(k = 20\) candidates to the re-ranker by
default (configurable per project).  This value balances recall coverage
and re-ranking latency: the BGE-reranker-v2-m3 cross-encoder processes 20
pairs in approximately 180\,ms on CPU, which is acceptable for interactive use.
The re-ranker produces a calibrated relevance score for each (query, passage)
pair; the top \(k' = 5\) passages are forwarded to the generation service.
All retrieval results are filtered by \texttt{project\_id} at the Weaviate
level, ensuring strict multi-tenancy.

\section{SSE Streaming Architecture}
\label{sec:sse_streaming}

In a conversational advisory system, perceived latency matters as much as actual
latency.  Displaying the first tokens of an answer within a second of submission ---
even though the full answer may take five to ten seconds to generate --- substantially
improves the user experience.  \medrag{} implements \emph{Server-Sent Events} (SSE)
streaming end-to-end: from the OpenAI SDK to the browser, without accumulating the
full response in memory at any intermediate service.

\subsection{Generation Service Streaming}

The generation service wraps the OpenAI Python SDK's streaming context
manager in an \texttt{AsyncGenerator}, yielding SSE-formatted byte strings.
\cref{lst:sse_generator} shows the core implementation.

\begin{figure}[htbp]
  \centering
\begin{lstlisting}[language=Python,
  caption={Core SSE streaming generator in the generation service.
    Token events are emitted as they arrive from the OpenAI SDK;
    the citations event is emitted once, after the stream completes.},
  label={lst:sse_generator}]
async def stream_response(
    prompt: str,
    model: str,
) -> AsyncGenerator[str, None]:
    async with client.messages.stream(
        model=model,
        max_tokens=1024,
        messages=[{"role": "user", "content": prompt}],
    ) as stream:
        async for text in stream.text_stream:
            yield (
                f"data: {json.dumps({'type': 'token', 'text': text})}\n\n"
            )
        final_msg = await stream.get_final_message()
        citations = extract_citations(final_msg)
        yield (
            f"data: {json.dumps({'type': 'citations', 'data': citations})}\n\n"
        )
    yield "data: [DONE]\n\n"
\end{lstlisting}
  \caption[Server-Sent Events streaming in the generation service.]{SSE streaming: token events are forwarded directly to the client; a \texttt{citations} event is emitted once after stream completion.}
  \label{fig:sse_streaming}
\end{figure}

The generator is wrapped in a FastAPI \texttt{StreamingResponse} with
\texttt{media\_type="text/event-stream"} and the required
\texttt{Cache-Control: no-cache} header.  Three event types are emitted on the stream.
\texttt{token} events carry one or more characters of generated text; the OpenAI SDK
may batch adjacent characters into a single event and the granularity is not guaranteed.
The \texttt{citations} event is emitted once, immediately after the stream completes,
carrying a JSON array of citation objects each containing the document chunk identifier,
the source document title, and the page number where available; it is extracted from the
final message object returned by \texttt{stream.get\_final\_message()}, which is
available only after the SDK has received the stop signal from the API.
Finally, \texttt{[DONE]} is the conventional SSE termination sentinel.

One deliberate design decision is to separate citation delivery from the token
stream rather than interleaving citation markers inline.  Inline markers require
the generation service to parse model output in real time, which is fragile and
model-specific.  Delivering citations as a single post-stream event lets the
front-end render the full answer first and then annotate it with source links,
which is more robust and requires no streaming-aware parsing on the back-end.

\subsection{Orchestrator Pass-through}

The orchestrator service does not buffer or transform the SSE stream.  On
receiving a streaming response from the generation service, it forwards the
\texttt{StreamingResponse} object directly to the API gateway, which in turn
forwards it to the browser.  This pass-through design keeps end-to-end latency
minimal and avoids the memory overhead that would arise from accumulating the
full response.  The orchestrator persists the completed conversation turn to
MongoDB only after the \texttt{[DONE]} event is received, using a background
task registered with FastAPI's \texttt{BackgroundTasks} mechanism.

\subsection{Front-end Handling}

The Next.js client opens an \texttt{EventSource} connection to the API gateway
and attaches a \texttt{message} listener.  Received events are parsed as JSON;
\texttt{token} payloads are appended to a React state string, causing a
progressive re-render of the answer panel; the \texttt{citations} payload
replaces a separate citations state array, triggering a single re-render of
the source list.  Streaming is initiated when the user presses the submit
button, which calls the front-end's \texttt{sendQuery} function and immediately
sets the UI into a \emph{streaming} state that shows a blinking cursor while
tokens arrive.

\section{RAGAS Evaluation Integration}
\label{sec:ragas_integration}

Measuring the quality of a RAG system requires metrics that assess not only
the final answer but also the quality of the retrieved context.  \medrag{}
integrates the RAGAS framework~\cite{es2023ragas} as an independent, asynchronous
evaluation service that does not affect the latency of query responses.

\subsection{Architecture}

The \texttt{eval} service (port 8013) operates as a RabbitMQ consumer.
Whenever a query completes, the orchestrator publishes a
\texttt{query.completed} event to the \texttt{medrag.events} exchange.  The
event payload is a JSON object carrying \texttt{conversation\_id} and
\texttt{message\_id} for linking results back to MongoDB, \texttt{question} as the
original user query string, \texttt{answer} as the generated response collected after
the SSE stream completes, \texttt{contexts} as a list of retrieved chunk strings passed
to the generation service, and an optional \texttt{ground\_truth} field present only
when the query originates from a benchmarking script that supplies reference annotations.

The eval service acknowledges the RabbitMQ message only after successfully
writing results to MongoDB, ensuring that no evaluation record is silently
lost due to a transient error.  Failed evaluations are requeued with a fixed back-off.

\subsection{Metrics}

\begin{figure}[htbp]
  \centering
  \begin{tabularx}{\textwidth}{lXlc}
    \toprule
    \textbf{Metric} & \textbf{Computation method} &
    \textbf{Requires \texttt{ground\_truth}} & \textbf{Approx.\ LLM calls} \\
    \midrule
    Faithfulness &
      Claim extraction from answer; NLI entailment check against each
      retrieved context chunk (LLM-as-judge) &
      No & 2 \\
    Answer Relevance &
      Cosine similarity between the embedding of the original question and
      embeddings of questions reverse-generated from the answer (LLM-as-judge) &
      No & 1 + embed \\
    Context Recall &
      Recall of ground-truth atomic statements that are attributable to at
      least one retrieved chunk (LLM-as-judge) &
      Yes & 1 \\
    Answer Correctness &
      Token-level F1 between the generated answer and the ground-truth
      answer (string matching; no LLM call) &
      Yes & 0 \\
    \bottomrule
  \end{tabularx}
  \caption[Evaluation pipeline and RAGAS metrics.]{RAGAS metrics computed by the eval service: computation method, ground-truth dependency, and approximate LLM call count per query.}
  \label{fig:ragas_pipeline}
\end{figure}

Faithfulness and Answer Relevance can be computed from the live system without
reference answers; they are therefore available for every query, including
interactive user sessions.  Context Recall and Answer Correctness require a
reference answer and are used only during benchmarking runs where ground-truth
data is available.

\subsection{Cost and Throughput}

RAGAS metrics that use the LLM-as-judge approach issue multiple LLM API calls
per question.  Based on observed token usage during benchmark runs on the
HotpotQA dataset, the combined cost of computing Faithfulness and Answer
Relevance is approximately \$0.006 per question.  For the full evaluation runs
reported in \cref{cha:evaluation} (500 questions), this corresponds to
roughly \$3 in API costs.  The asynchronous design means that evaluation
does not compete with query latency for API capacity: the eval service has its
own rate-limit headroom and processes questions at a pace independent of the
interactive query load.

Results are stored as documents in the MongoDB \texttt{eval\_results} collection.
Each document records the metric scores, the RAGAS library version, the timestamp,
and the identifiers required to join back to the conversation and the project settings,
enabling post-hoc analysis across experimental conditions.

\section{CI/CD Pipeline}
\label{sec:cicd}

Maintaining confidence in a codebase spanning fourteen services and two
languages requires automated quality gates at every pull request.  \medrag{}
uses two GitHub Actions workflows: a \emph{continuous integration} workflow
that validates correctness, and a \emph{continuous deployment} workflow that
validates the Docker build and runtime health of the full stack.

\subsection{Continuous Integration}

The CI workflow (\texttt{.github/workflows/ci.yml}) is triggered on every
pull request targeting \texttt{develop} or \texttt{main} and runs four stages
in parallel where possible.
\textbf{Linting and formatting} (\texttt{ruff check} and \texttt{ruff format --check})
enforces the project's style conventions; \texttt{ruff} is preferred over the
\texttt{flake8}+\texttt{black} combination because it implements both tools in a
single Rust binary, reducing CI step time from roughly 40 seconds to under 5 seconds.
\textbf{Static type checking} (\texttt{mypy} in strict mode) catches type errors and
missing annotations; strict mode is applied from the outset rather than incrementally,
to prevent the gradual accumulation of untyped code.
\textbf{Unit and integration tests} (\texttt{pytest}) are run only for services modified
in the pull request, reducing feedback time on small changes; services without a
\texttt{tests/} directory are skipped without failure.
\textbf{Front-end validation} runs \texttt{tsc --noEmit}, \texttt{eslint}, and
\texttt{vitest run}, but only when files under \texttt{frontend/} have been modified.
The \texttt{ANTHROPIC\_API\_KEY} secret is stored in the GitHub repository's encrypted
secret store and injected into the environment for any integration tests that issue
real API calls.

\subsection{Continuous Deployment}

The CD workflow (\texttt{.github/workflows/cd.yml}) is triggered on every push to
\texttt{develop}, ensuring the integration branch always produces a runnable image
set, and performs three steps.
First, \texttt{docker compose build} exercises every service's multi-stage Dockerfile;
a failure here indicates a broken dependency declaration or an invalid Dockerfile
instruction.
Second, \texttt{docker compose up -d} brings up all fourteen containers, with Compose's
dependency-ordering logic ensuring that databases and the message broker are healthy
before dependent services start; a polling loop then issues \texttt{curl} requests to
each service's \texttt{/health} endpoint until all return \texttt{\{"status": "ok"\}}
or a timeout is exceeded.
Third, \texttt{docker compose down} removes all containers and networks, leaving the
CI runner in a clean state.

This \emph{smoke test} strategy does not replace unit or integration tests, but it
provides a fast check that the containerised system starts and that all services
are reachable.  In practice, the most common failures caught at this stage are
missing environment variables and Weaviate schema migration errors that only manifest
at container start-up.

\subsection{Branch and Merge Strategy}

The repository follows a structured branching model.  Feature work is conducted on
branches named \texttt{feature/phase-X.Y-description} and merged into
\texttt{develop} via pull request; the CI workflow must be green before merge is
permitted.  The \texttt{main} branch receives merges from \texttt{develop} only when
a full phase is demo-ready, and is tagged with a version identifier such as
\texttt{v0.7-phase-7-done}.  Both protected branches require at least one approving
review and passing status checks, enforced by GitHub's branch protection rules.
